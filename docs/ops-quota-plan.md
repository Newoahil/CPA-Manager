## 1. 背景

团队在 Dokploy 上部署了 CPA（CLIProxyAPI v8 fork，分支 `codex/v8-dokploy-update`），用来统一使用 Claude、Codex、Gemini CLI、Antigravity 等包月订阅账号。CPA-Manager 是部署在旁边的监控程序，目前能做到：

- 每 15 分钟查询一次每个订阅账号的额度（已用百分比、重置时间）；
- 额度超过阈值、账号失效、采集异常时发飞书告警；
- 每天 10:00、17:00 发额度日报；
- 飞书 @机器人 查询当前额度和异常。

现在有两类新需求：

1. **CPA 运维**：账号失效、服务不可用、请求失败率异常都要能及时发现。上游有新版本时要提醒。部分运维操作希望经飞书审批后由系统执行。
2. **额度管理**：发现额度"用得太快"（重置前会用满）和"用不完"（订阅浪费），并定期回答"团队订阅够不够用"。

另外，团队要求接入审计日志平台（audit-logger-agent），所有运维操作都要留下可追溯的记录。

"按项目统计消耗"已讨论过，**本期搁置**，见第 2 节非目标。

## 2. 目标与非目标

### 目标

| 编号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | 账号健康异常（失效、禁用、冷却、刷新失败）能主动告警 | 异常出现后，最多两个采集周期内收到飞书告警 |
| G2 | CPA 服务、管理接口不可用，或 CPA-Manager 自身采集中断时能告警 | 模拟 CPA 停机能收到告警；恢复后收到恢复通知 |
| G3 | 请求失败率突增能告警 | 基于 CPA 最近约 3 小时、每 10 分钟一段的成功/失败计数判断 |
| G4 | 上游 CPA 发布新版本时提醒 | 上游有新 Release 时发一次提醒，同一版本不重复 |
| G5 | 实时提醒额度"用得太快" | 按当前消耗速度，预测会在重置前用满时提醒 |
| G6 | 实时提醒额度"用不完" | 只看 7 天这类长窗口；快重置时预计还剩很多，就提醒一次 |
| G7 | 每周发周报，回答"订阅够不够用" | 每周一（可配置）发出，包含每个账号的用满次数、平均使用率和加号/减号建议 |
| G8 | 飞书卡片审批后执行运维操作 | 禁用/启用账号、刷新 token、升级、回滚都必须经卡片批准才执行 |
| G9 | 上游升级半自动化 | agent 合并上游并开 PR；批准后合并、自动部署、自动做部署后检查 |
| G10 | 接入团队审计日志平台 | 审计平台 Dashboard 中能看到 `cpa-manager` 和 `cpa-upgrade-agent` 的完整链路 |

### 非目标

- **按项目统计消耗**：本期不做。CPA 没有"项目"概念；cpamp 已能按客户端 Key 统计用量，以后立项时直接读 cpamp，并在 cpa-buddy 维护"Key → 项目"对照表。
- **删除账号、修改 CPA 配置**：不提供。删除不可恢复；CPA 配置在部署时由环境变量覆盖，在线修改会被下次部署还原（见 5.3）。
- **改造 cpamp 代码**：不 fork、不 cherry-pick，只使用官方镜像和它的 HTTP 接口。
- **按量付费的 API Key 的额度判断**：不判断"够不够用"，因为它们没有额度上限的问题。
- **状态页（:8080）图表**：后续再做。
- **"屏蔽 Claude/GPT 模型分组"**：由另一个 agent 负责，不在本方案范围内。
- **本地审批权限控制**：不做，依赖飞书会话成员管理，见 5.1。

## 3. 现状分析

### 3.1 CPA 已开放的能力

以下都在 CPA 管理接口中，鉴权方式为 `Authorization: Bearer <管理密钥>` 或 `X-Management-Key`：

| 用途 | v8 接口 | 说明 |
| --- | --- | --- |
| 账号列表 | `GET /v8/management/credentials` | 分页，含状态、`unavailable`、冷却信息、`auth_index` |
| 额度查询 | `POST /v8/management/requests/api-call` 等 | CPA 不内置四家额度查询，CPA-Manager 通过代发请求用账号自己的 token 去查 |
| 请求成功/失败计数 | `GET /v8/management/observability/usage/api-keys` | 每 10 分钟一段，共 20 段（约 3 小时）；只在内存中，重启清零；读取不消耗数据 |
| 禁用/启用账号 | `PATCH /v8/management/credentials/status` | 写操作 |
| 刷新 token | `POST /v8/management/credentials/refresh` | 写操作 |
| 上游最新版本 | `GET /v8/management/server/latest-version` | 查的是官方上游仓库的最新 Release |
| 当前运行版本 | 每个管理接口响应头 `X-CPA-VERSION`、`X-CPA-COMMIT` | 可用来确认部署后的新版本已经运行 |

需要注意：

- 管理接口鉴权失败次数过多，CPA 会**封禁来源 IP**（返回 403）。CPA-Manager 已对 401/403 做全局退避，新增的写操作也必须遵守。
- 每条请求的详细用量记录（token 数、模型、调用方 Key）默认关闭，开启后只在内存队列中保留一段时间（现设 600 秒，最多 3600 秒），**读取即取走**。现在由 cpamp 独占读取，cpa-buddy **不得**再读这个队列。

### 3.3 cpamp 提供的能力

cpamp 是独立服务，通过 CPA 的 `/v0/management` 接口连接（本 fork 同时保留 v0 和 v8），用自己的 SQLite（`/data` 卷）保存数据。cpa-buddy 用 `Authorization: Bearer <cpamp 管理员密钥>` 读取它的接口：

| 数据 | cpamp 接口 | 用途 |
| --- | --- | --- |
| 用量统计（调用数、token、费用，按 Key / 模型 / 账号 / 时间段） | `POST /v0/management/monitoring/analytics` | 失败率告警、周报用量部分、以后的按项目统计 |
| 最近失败明细 | 同上，`include.recent_failures` | 告警内容中说明失败原因 |
| 账号问题队列（需重新登录 / 删除 / 复查） | `GET /v0/management/account-action-candidates` | 账号健康告警的补充来源 |
| Codex 额度历史 | `POST /v0/management/quota-snapshots/query` | 仅在 cpamp 开启 Codex 巡检时可用，本期不依赖 |
| cpamp 自身采集状态 | `GET /status` | 判断"用量数据是否中断" |

cpamp **给不了**、仍由 cpa-buddy 负责的：
- Claude、Antigravity、Gemini CLI 的后台额度采集（cpamp 只在有人打开网页账号页时采集，Gemini CLI 不支持）；
- 速度预测、主动提醒、周报、飞书、审批、审计；
- 操作人记录（cpamp 不记录谁做了什么）。

cpamp 的约束：
- 只有一个管理员密钥，且会把未接管的 `/v0/management/*` 请求原样转发给 CPA，**拿到它等于拿到 CPA 全部管理权限**。密钥只由 cpa-buddy 持有，cpa-buddy 只调用上表中的只读接口。
- 自动写 CPA 的功能全部关闭：`USAGE_ACCOUNT_ACTIONS_AUTO_DISABLE=false`、`USAGE_QUOTA_COOLDOWN_ENABLED=false`，Codex 巡检自动动作为"无"。
- 没有推送或事件游标，cpa-buddy 只能定时拉取，自己判断哪些是新问题。
- cpamp 停机超过队列保留时间，或 CPA 重启，期间的用量记录会丢失。

### 3.2 CPA-Manager 现有能力与差距

| 能力 | 现状 | 差距 |
| --- | --- | --- |
| 额度数据 | 每 15 分钟采集一次，**只保存最新一次结果** | 没有历史数据，无法计算消耗速度和周统计 |
| 账号健康 | 能识别 401（凭证失效），会在额度通知里顺带提及 | 禁用、冷却、刷新失败没有独立告警 |
| 服务健康 | 连续采集失败会标记为"数据过期" | 没有明确的"CPA 不可用"告警和恢复通知 |
| 失败率 | 有异常判断逻辑，但没有接入 CPA 的成功/失败计数 | 需要接入数据源 |
| 版本 | 无 | 需要新增 |
| 预测与周报 | 只有阈值告警（v1.0 默认 80/90/100）、快速轮询和日报 | 没有消耗速度预测，也没有周报 |
| 写操作 | 设计上只读，不改变 CPA 状态 | 需要新增审批执行机制 |
| 审计日志 | 无 | 需要新增 |
| 飞书卡片回调 | 已有"刷新额度"按钮回调，回调后先应答再异步刷新 | 可以复用来做审批按钮 |

## 4. 方案设计

### 4.0 与 v1.0 的衔接（依据 v1.0 交付契约，基线 `9bec082`）

**v1.0 已有、v2.0 直接复用**
- 冷却 / 限流告警、快速轮询（任一窗口达提醒线后改用 `FAST_POLL_INTERVAL`）、日志留档 `/data/logs`。
- 阈值默认已改为 80 / 90 / 100（提醒 / 告警 / 用满）。
- 扩展方式：新周期信号参照 cooldown，写独立循环 → `enqueueAlerts` 进 outbox → 新增 `AlertKind` → `defaultTitles` 和 `alertKindPhrase` 补文案；新卡片类型新建文件，在 `cardElements` 开头按 `Message.Kind` 分支。

**v2.0 必须先处理的 v1.0 遗留**
1. **屏蔽分组的告警被过滤后，会推出一整张额度卡**：发送前判断"原消息有告警、过滤后为空"就不发。属于线上缺陷，建议作为 v1.0.1 修复，不等 v2.0。
2. **卡片回调路由改成注册表**：`handler.go` 现在是 if 链，先重构成"action → handler"，再注册批准 / 拒绝。
3. **回调记录来源**：审批点击要记录操作人和来源会话，写入审计；不做本地权限校验，见 5.1"谁能批准"。
4. **审批的去重键**：v1.0 按"消息 ID + action"去重，同一卡片同一按钮只处理一次。审批改用 `decision.id`，状态以持久化的审批记录为准。
5. **屏蔽分组只在渲染层生效**：v2.0 的速度预测、"用不完"、周报统计都要在计算时排除屏蔽分组，否则会对不用的分组报"浪费"。
6. **状态网页 `/`、`/api/status` 没有登录**：v2.0 不在上面加任何写操作或敏感数据。

**v2.0 不碰的**：`internal/evaluate`、`internal/state` 的 JSON 字段名、`app.go` 的锁顺序（`persistMu` → `outboxMu`）和 outbox、`internal/quota` 与 `internal/cpa` 的解析逻辑、`render/blocks.go` 和 `alertnotice.go` 的行系统。额度历史、审批记录、审计队列都放新文件，不改 `state.json`。

### 4.1 整体结构

数据层：cpamp 负责用量统计；cpa-buddy 负责额度采集、判断、通知、审批和审计。cpa-buddy 的 compose 中将来再加一个升级 agent 容器（第 4 期）：

```text
cpa ──用量队列──▶ cpamp（官方镜像） ──HTTP 只读接口──▶ cpa-buddy
 ▲                                                  │
 └──── 额度查询（api-call）、审批后的写操作 ─────────────┘
```

cpa-buddy 内部结构如下：

```text
                    ┌──────────────── 飞书会话（CPA-Manager 现有配置）────────────────┐
                    │   告警 / 周报 / 查询回复 / 审批卡片（批准、拒绝）                │
                    └───────────────▲──────────────────────────┬──────────────────────┘
                                    │                          │ 卡片回调
┌───────────────────────────────────┴──────────────────────────▼───────┐
│ CPA-Manager（现有服务，扩展）                                          │
│  采集 → 额度历史 → 判断（阈值/速度/健康/失败率/版本）→ 通知             │
│  审批中心：发卡片 → 收回调 → 校验批准内容 → 执行 → 验证 → 记录          │
│  审计模块：本地 NDJSON → 异步发送审计平台 → 失败重试                    │
└───────┬───────────────────────────────────────────────┬──────────────┘
        │ 管理接口（读 + 审批后的写）                    │ 内部接口：触发升级、汇报进度
        ▼                                               ▼
┌──────────────┐                               ┌──────────────────────────────┐
│ CPA          │◄─── 大模型调用（暂走 CPA）──────│ 升级 agent（新服务）           │
│ cli-proxy-api│                               │ git + Go 1.26 + 大模型        │
└──────▲───────┘                               │ 合并上游 → 测试 → 开 PR        │
       │ Dokploy 推送后自动部署                 └──────────────┬───────────────┘
       └──────────────── GitHub: Leejhua/CLIProxyAPI ◄─────────┘
```

- **CPA-Manager** 是唯一的飞书入口，也是唯一会调用 CPA 写接口的程序。
- **升级 agent** 的代码放在本仓库（如 `cmd/cpa-upgrade-agent`），单独打镜像。它不直接发飞书消息，也不直接合并 PR；所有需要人批准的步骤都交回 CPA-Manager 发卡片。
- 两者分开部署：升级 agent 出问题，不会影响额度监控。

### 4.2 分期计划

| 期 | 内容 | 是否写 CPA | 依赖 |
| --- | --- | --- | --- |
| 第 1 期 自适应采集 | 额度历史、按账号分档采集、上游限速、被动信号、cpamp 提前发现、速度预测告警 | 否 | 无 |
| 第 2 期 运维监控 | 账号健康、服务健康、失败率、版本提醒、审计日志模块、维护期静音 | 否 | 第 1 期 |
| 第 3 期 额度管理 | "用不完"提醒、周报、机器人新查询 | 否 | 第 1 期 |
| 第 4 期 审批与升级 | 审批卡片框架、禁用/启用、刷新 token、升级 agent、部署后检查、回滚 | 是 | 第 1、2 期 |

第 2 期和第 3 期互不依赖，可以并行开发。

### 4.3 第 1 期：自适应采集（2026-10-09 确认）

现状：全局一个采集间隔（15 分钟），任一窗口过提醒线就把**所有号**改成 3 分钟。新方案改为**每个号按自己的状态定间隔**，替代现有的全局快速轮询（`FAST_POLL_INTERVAL`）。

**额度历史**（决定 Q6=A）
- 每次采集成功后，为每个号的每个窗口记一条：时间、已用百分比、刷新时间、窗口长度、来源（主动 / 被动 / cpamp）。
- 存 `/data/history/quota-YYYY-MM-DD.jsonl`，按天分文件，默认保留 90 天，过期删整天的文件。
- 不改 `state.json`；单副本、单写入者约束不变。

**分档**（决定 Q1=C：用量 + 速度一起看；Q2：闲置改为 30 分钟）

| 档位 | 进入条件 | 默认间隔 |
| --- | --- | --- |
| 闲置 | 连续 3 次采集用量没变 | 30 分钟 |
| 正常 | 其他情况 | 15 分钟 |
| 活跃 | 最近两次采集用量在涨，或 cpamp 显示该号最近 10 分钟有请求 | 5 分钟 |
| 盯防 | 按当前速度预计刷新前用完，或任一窗口剩余 < 20%，或 cpamp 显示请求量突增 | 2 分钟（受下方上游下限约束） |
| 已用满 / 被 CPA 暂停 | — | 不主动采，到刷新或恢复时间再采一次 |

- 档位只往上跳得快：发现盯防条件立刻升档；降档要连续两次不满足，避免来回抖动。
- 速度用最近 N 次（默认 3 次、至少跨 10 分钟）的已用百分比变化估算；样本不足或窗口刚刷新时不估算。
- 屏蔽分组（`QUOTA_IGNORED_GROUPS`）的窗口不参与分档和速度计算。

**上游限速**（决定 Q3=A，依据调研见 4.3.1）
- 每家一个最短主动间隔，档位间隔小于它时按它算：

  | Provider | 最短主动间隔（初稿） | 原因 |
  | --- | --- | --- |
  | Codex | 2 分钟 | usage 接口未见限流；另有被动信号 |
  | Claude | 10 分钟 | usage 接口会返回 429 + `Retry-After`（CodexBar 有专门熔断）；靠被动信号补实时性 |
  | Gemini CLI / Antigravity | 15 分钟 | 查询会在 token 临近过期时触发 OAuth 刷新，有写副作用 |
  | Ollama | 30 分钟 | 网页抓取，对突发敏感 |

- 全局：主动额度查询并发 ≤ 2；每分钟总次数有上限（默认 4，可配置），超出的排队顺延，优先级 盯防 > 活跃 > 正常 > 闲置。
- 收到 429 或 `Retry-After`：该号按 `Retry-After` 退避（没有则 5 分钟起指数退避，最长 30 分钟），期间只用被动信号。

**被动信号（调研新发现，优先使用）**
- CPA 在正常模型调用的响应头里抓取 Claude 的 `anthropic-ratelimit-unified-*` 和 Codex 的 `x-codex-*`，并放在管理接口凭证列表的 `quota` / `model_quotas`（含 `observed_at`）里。
- cpa-buddy 的冷却巡检本来就每 60 秒读一次凭证列表，顺便读这两项，**Claude 和 Codex 几乎零成本就有接近实时的用量**；主动查询退为兜底和校准（被动信号缺失或超过 10 分钟未更新时才主动查）。
- Gemini CLI、Antigravity、Ollama 没有被动信号，只能主动查。
- 被动信号的字段和准确度需要先用真实数据核对，再决定在卡片上是否和主动结果同等对待。

**cpamp 提前发现**（决定 Q4=A）
- cpa-buddy 每分钟读 cpamp 的 `monitoring/analytics`（按凭证统计最近 10 分钟请求数）。
- 请求量明显上升的号直接升到"活跃"或"盯防"，不等下一次采集。
- `CPAMP_BASE_URL` 为空或 cpamp 不可达时，这部分不生效，其余逻辑照常；不替换现有采集路径。

**速度预测告警**（决定 Q5=A：新增，现有阈值告警保留）
- 新告警类型"预计用完"：按当前速度，预计在窗口刷新前用完时推一次，写明预计用完时间和刷新时间。
- 每个号每个窗口周期最多推一次；scope 未知或证据不足时标"疑似"、不给建议。
- 先和 80/90/100 阈值告警并行运行，观察一段时间准确率后再决定是否替换 80% 提醒线。

#### 4.3.1 上游限速调研摘要

- Claude OAuth usage 接口会对轮询返回 429，并带 `Retry-After`；CodexBar 默认熔断 5 分钟。
- Codex usage 接口未见限流记录，也不带限流头；`x-codex-*` 来自正常模型流量。
- Gemini CLI、Antigravity 查询在 token 快过期时会触发 OAuth 刷新并回写凭证，高频轮询会放大这个副作用。
- 未发现查询额度接口本身计入模型额度或导致封号的证据，但官方没有声明【未验证】。
- CodexBar 自适应间隔为 2 / 5 / 15 / 30 分钟，范围 2–30 分钟，与本方案分档一致。

**审计日志模块**（移到第 2 期，详见第 6 节）
- 两个服务共用同一个 Go 包。
- 先写本地 `audit-YYYY-MM-DD.jsonl`，再异步发送到审计平台。发送失败进入重试队列，不影响业务。

**维护期静音**（移到第 2 期）
- 进入维护期（批准升级或回滚后自动进入，默认 10 分钟，可配置）后，暂停"服务不可用"和"采集失败"类告警。
- 维护期只等待部署后检查的结果；维护期结束仍不健康，就恢复正常告警。

### 4.4 第 2 期：运维监控

| 监控项 | 数据来源 | 告警条件（默认值可配置） | 恢复通知 |
| --- | --- | --- | --- |
| 账号失效 | 额度查询返回 401、账号列表状态 | 第一次发现时 | 有 |
| 账号禁用 | 账号列表 `disabled` | 状态从启用变为禁用时 | 有 |
| 账号冷却 | **v1.0 已实现**（`internal/cooldown`，`AlertRateLimited` / `AlertRateLimitCleared`），v2.0 只补持久化，重启后不丢计时 | 冷却持续 ≥ `COOLDOWN_ALERT_AFTER` | 有 |
| token 刷新失败 | 账号列表状态和错误信息 | 第一次发现时 | 有 |
| CPA 不可用 | 管理接口连接失败或 5xx | 连续两次失败 | 有 |
| 管理鉴权失败 | 401/403 | 第一次发现时；同时提示检查管理密钥，避免 IP 被封 | 有 |
| 采集中断 | CPA-Manager 自身采集循环 | 超过两个采集周期没有完成采集 | 有 |
| 失败率突增 | 优先 cpamp `monitoring/analytics`（含失败明细）；cpamp 不可用时退回 CPA `observability/usage/api-keys` 的 10 分钟分段 | 最近 30 分钟失败率超过阈值，且请求数达到最小样本量 | 有 |
| 用量数据中断 | cpamp `GET /status` 的最后采集时间和错误 | cpamp 不可达，或超过一定时间没有新用量入库 | 有 |
| 上游新版本 | `server/latest-version` 与 `X-CPA-VERSION` 对比 | 上游版本高于当前运行版本；每天最多检查一次，同一版本只提醒一次 | — |

上游新版本提醒卡片上带"准备升级"按钮，点击后进入第 4 期的升级流程。

### 4.5 第 3 期：额度管理

**消耗速度预测（实时）**
- 用最近一段历史记录估算当前消耗速度：已用百分比随时间的变化。
- **用太快**：按当前速度，预计在窗口重置前用满。每个账号的每个窗口周期内最多提醒一次，消息中写明预计用满时间和建议改用的账号。
- **用不完**：只针对 7 天这类长窗口，5 小时窗口不提醒。距重置不足一定时间（如 24 小时）、且预计重置时剩余超过阈值（如 50%）时提醒一次，提示"可以优先使用这个号"。
- 样本不足（历史记录少于一定数量，或窗口刚重置）时不预测，避免误报。

**周报**
- 默认每周一 10:00 发出（可配置），统计上一周数据：
  - 每个账号、每个窗口用满了几次，平均和峰值使用率；
  - 失效、冷却、不可用的时长；
  - 本周调用量、token 和费用，按模型、按账号的分布（来自 cpamp）；
  - 结论：哪类订阅不够（经常用满），哪类有富余（平均使用率低），给出加号或减号建议。
- 同时保留现有日报。

**机器人新查询**
- "本周额度够不够"：返回本周至今的周报摘要；
- "哪个号失效了"：返回当前账号健康异常列表；
- 以及与上面监控项对应的查询。具体问法沿用现有关键词识别方式。

### 4.6 第 4 期：审批与升级

**审批卡片通用流程**

```text
发现问题或用户发起
  → 生成"待执行操作"（类型、目标账号、参数）
  → 对操作内容计算指纹（subject_hash）
  → 发审批卡片（说明原因、影响、过期时间），状态：待批准
  → 用户点"批准"或"拒绝"
  → 校验：未过期、未重复处理、指纹与当前操作一致
  → 执行 → 执行后验证 → 更新卡片显示结果、批准人和时间
```

- 审批卡片发到 CPA-Manager 现在配置的飞书会话中。
- 卡片默认 30 分钟后过期（可配置）。过期或已处理的卡片再被点击，只提示状态，不会再次执行。
- 执行前如果发现目标状态已经变化（例如账号已被别人手动禁用），旧审批作废，需要重新发卡片。
- 待审批记录要持久化，CPA-Manager 重启后，未过期的审批仍然有效。

**支持的操作**

| 操作 | 触发 | CPA 接口 | 执行后验证 |
| --- | --- | --- | --- |
| 禁用账号 | 账号失效、持续异常时系统建议；或用户在机器人中发起 | `PATCH credentials/status` | 重新读取账号列表，确认已禁用 |
| 启用账号 | 用户发起；或已禁用账号恢复时系统建议 | `PATCH credentials/status` | 确认已启用，下一轮采集正常 |
| 刷新 token | 刷新失败或 401 时系统建议 | `POST credentials/refresh` | 下一轮额度查询不再返回 401 |
| 准备升级 | 新版本提醒卡片 | —（触发升级 agent） | agent 开出 PR |
| 合并升级 | 升级 agent 开 PR 后 | GitHub 合并 PR | Dokploy 部署后检查通过 |
| 回滚 | 部署后检查不通过 | GitHub 撤销该次合并 | 回到旧 commit 并检查通过 |

**升级流程**

```text
发现上游新版本 → 提醒卡片"准备升级"
  → 批准 → 升级 agent：拉取 fork 和上游，合并，Go 1.26 编译测试，生成升级说明，开 PR
  → CPA-Manager 发卡片（附 PR 链接、改动摘要、冲突处理说明、测试结果）"合并并部署"
  → 批准 → 合并 PR → Dokploy 自动部署 → 进入维护期静音
  → 部署后检查（固定规则，不用大模型）：
       X-CPA-COMMIT 变为新 commit；管理接口可用；账号列表正常；
       额度采集正常；失败率没有明显上升
  → 通过：发"升级完成"；不通过：发"回滚"审批卡片
```

- 大模型只在部署前使用。部署期间和部署后检查都不需要大模型，所以即使大模型暂时走 CPA，CPA 重启也不影响流程。
- 升级 agent 需要的环境：git、Go 1.26、能开 PR 和合并 PR 的 GitHub token、大模型 Key（暂时用 CPA 的客户端 Key，之后切到独立 Key）。
- **合并冲突的处理策略、升级 agent 的内部实现，在第 4 期开工前单独讨论。**

## 5. 边界情况、异常流与兼容性

### 5.1 边界情况处理

| 情况 | 处理 |
| --- | --- |
| 审批卡片被重复点击 | 只执行一次；后续点击只显示"已由某人于某时批准" |
| 多人同时点批准和拒绝 | 以第一个到达的为准，其他人看到最终状态 |
| 卡片过期后被点击 | 不执行，提示已过期，需要重新发起 |
| 批准后目标状态已变化 | 旧审批作废，重新发卡片 |
| 同一账号已有待审批操作 | 不再发同类卡片，避免刷屏 |
| 历史记录不足、窗口刚重置 | 不做速度预测 |
| 额度数据缺失（未上报） | 不当作 0，不参与预测，与现有规则一致 |
| 范围未知的额度窗口（`scope=unknown`） | 可以提醒速度，但不建议禁用整个账号，与现有规则一致 |
| 账号被禁用 | 不采集额度，不参与预测和"用不完"提醒；周报中单独列出 |
| 谁能批准 | 不做本地权限校验，权限依赖飞书侧配置。每次点击都记录批准人、来源会话和时间，写入审计 |

### 5.2 异常流

| 异常 | 用户可见结果 | 系统记录 | 恢复方式 |
| --- | --- | --- | --- |
| 执行写操作时 CPA 返回错误 | 卡片显示"执行失败"和 CPA 返回的原因 | 审计记录 `tool.error`，带状态码 | 可重新发起 |
| 管理鉴权 401/403 | 告警提示检查管理密钥 | 进入全局退避，不重试写操作 | 修正密钥后自动恢复 |
| 升级 agent 编译或测试失败 | 卡片显示"升级准备失败"和失败摘要，不开 PR | 审计记录 `run.failed` | 人工处理后重新发起 |
| 合并冲突超出 agent 处理范围 | 卡片显示冲突文件，需要人工处理 | 审计记录 | 策略待第 4 期细化 |
| GitHub 不可用、token 失效 | 卡片显示失败原因 | 审计记录 | 修复后重新发起 |
| 部署后检查不通过 | 发回滚审批卡片 | 审计记录检查结果 | 批准回滚 |
| 维护期结束仍不健康 | 恢复正常告警 | — | 人工排查 |
| 审计平台连不上 | 无感知，业务照常 | 本地 NDJSON 保留，进入重试队列 | 恢复后自动补发 |
| 审计重试队列积压过多 | 发一条告警 | — | 排查审计平台 |
| CPA-Manager 在审批过程中重启 | 未过期的审批仍可点；执行中途重启的操作，重启后先核对目标实际状态再更新卡片 | 审计记录 `run.resume` | 自动 |

### 5.3 对现有功能的影响

- **现有告警、日报、机器人查询**：行为保持不变，新功能只增加消息类型。
- **现有采集路径不变**：cpa-buddy 继续直接读 CPA 管理接口采集账号和额度，开发期间不改这条路径。读取 cpamp 只作为新增数据源，`CPAMP_BASE_URL` 为空时完全不启用。新功能可用并稳定后，再逐项评估哪些数据迁到 cpamp；额度采集要等 cpamp 支持 Claude、Antigravity、Gemini CLI 的后台采集后再考虑。
- **只读原则**：CPA-Manager 原来承诺"不改变凭证状态"。本方案改为"**只有经卡片审批后才会写**"，README 中的"行为边界"一节需要同步修改。
- **配置**：新增配置都有默认值；不配置时，第 2、3 期功能按默认值启用；审批写操作和升级必须显式开启（如 `OPS_ACTIONS_ENABLED`、`UPGRADE_AGENT_URL`），未开启时不发审批卡片。
- **状态文件**：现有 `/data` 中的状态文件格式不变，新增文件不需要迁移历史数据。额度历史从上线时开始积累，**上线后第一周的周报和速度预测数据不完整**，周报中会注明。
- **render 相关文件**：另一个 agent 正在修改 `internal/notify/render`。本方案尽量新增文件，不改那几个文件；必须改时先与该任务协调。
- **CPA 配置覆盖隐患（已知，未根治）**：当前 fork 启动时，会用环境变量生成的配置**整份覆盖** `cpaDB` 中的配置（`cmd/server/main.go:477-485`）。原先只配了 `CLI_PROXY_API_KEYS_JSON`，因此面板里热更新的配置（包括用量统计开关）每次重新部署都会丢失。临时处理：已把当前完整配置写入 `CLI_PROXY_CONFIG_B64`。**此后在 CPA 面板改配置，必须同步更新该环境变量。** 根治方案是修改 fork 的启动逻辑，以数据库中的配置为准（与被 revert 的 `c5922450` 目标相同），需挑维护窗口部署，见第 9 节。
- **cpamp 依赖 CPA 用量统计开关**：开关被还原后，cpamp 仍在运行，但收不到新数据。cpa-buddy 的"用量数据中断"告警（4.4）用来发现这种情况。

### 5.4 灰度与回滚

- 每类新功能都有独立开关，可以单独关闭。
- 审批写操作默认关闭，确认稳定后再开启。
- 升级 agent 是独立服务，停掉它不影响监控。
- 出问题时回退 CPA-Manager 镜像即可。新增的数据文件不影响旧版本运行。

## 6. 接口与数据契约

### 6.1 审计日志（对接 audit-logger-agent）

按团队《将任意 Agent 改造成可发送审计日志的 Agent》规范实现。

| 项 | 约定 |
| --- | --- |
| `agent_id` | `cpa-manager`、`cpa-upgrade-agent` |
| 接收地址 | 配置 `AUDIT_INGEST_URL`（完整的 `/v1/ingest` 地址）；为空时只写本地 |
| 本地目录 | `/data/audit/`，文件名 `audit-YYYY-MM-DD.jsonl`，另有重试队列文件 |
| 发送 | 单事件发送；只有 `accepted == 1 && rejected == 0` 才算成功；400/413/415 不做快速重试 |
| 重试 | 重发完全相同的原始数据；每轮最多 `AUDIT_RETRY_MAX_BATCH`（默认 50）条 |
| 版本 | `schema_version: 2`，每条带 `producer_event_id` |

**记录范围**

| 场景 | 链路 |
| --- | --- |
| 审批操作 | `run.start` → `agent.start` → 预览 `tool.end` → `run.waiting_user`（`decision.id`、`subject_hash`）→ `run.resume`（批准人）→ 执行 `tool.start/end`（`authorization_ref`）→ 验证 `tool.start/end` → `agent.end` → `run.final_result` |
| 告警和周报 | 每次发送一条链路，工具名如 `notification.alert.send`、`notification.report.send` |
| 采集 | 只记录失败的采集 |
| 升级 | 从"准备升级"到部署后检查，用**同一个 `trace_id`**；升级 agent 的事件挂在 CPA-Manager 委派的 Span 下 |

**工具名（示例）**：`cpa.credential.list`、`cpa.credential.disable`、`cpa.credential.enable`、`cpa.credential.token.refresh`、`github.pr.create`、`github.pr.merge`、`service.deploy.verify`、`service.rollback`、`notification.alert.send`。

**脱敏**：不记录管理密钥、账号 token、客户端 API Key、完整请求和响应内容、邮箱原文。账号统一使用现有的不透明 Key 或别名。审计平台目前是 http 且没有来源认证，所以日志只能视为"生产者声明"。

### 6.2 CPA-Manager 与升级 agent 之间

- 走同一 compose 网络内的内部 HTTP 接口，不对外暴露，用共享密钥鉴权。
- CPA-Manager → agent：发起升级准备（带 `trace_id`、目标版本）。
- agent → CPA-Manager：上报进度和结果（PR 链接、改动摘要、测试结果、失败原因）。
- 具体接口在第 4 期细化。

| `AUDIT_RETRY_ENABLED` / `AUDIT_RETRY_MAX_BATCH` | `true` / `50` | 审计重试 |
| `CPAMP_BASE_URL` | 空 | cpamp 内部地址，如 `http://cpamp:18317`；为空时不读 cpamp，相关功能退回 CPA 数据或不启用 |
| `CPAMP_ADMIN_KEY` | 空 | cpamp 管理员密钥，只用于只读接口 |

升级 agent 另需：`GITHUB_TOKEN`、目标仓库和分支、上游仓库地址、大模型地址和 Key。

## 8. 上线顺序

### 8.1 分支与环境（待 v1.0 收尾后落实）

| 分支 | 用途 | 部署 |
